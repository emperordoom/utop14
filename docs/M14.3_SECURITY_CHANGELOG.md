## Security Controls Delivered Through PR #14

### Authentication Abuse & Identifier Privacy
- Enforced PostgreSQL-backed fixed-window login rate limiting across identifier, IP, and combined scopes with HTTP `429` throttling and cooldown windows.
- Reused the existing M14.1 `SECURITY_EVENT_HASH_KEY` (already validated since M14.1 as at least 32 bytes, distinct from `SECRET_KEY`, and non-placeholder in production) to derive domain-separated HMAC-SHA256 bucket keys (`utop14.auth_rate_limit.v1`) for `auth_rate_limits`, ensuring raw email addresses and IP addresses are never stored in the rate-limit table.

### Application and Retention Role Least Privilege
- Enforced `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, and `NOINHERIT` on `utop14_app`, `utop14_retention_owner` (`NOLOGIN`), and `utop14_retention_runner` (`LOGIN`).
- Enforced default-deny recursive role memberships (including direct, transitive, `SET`/`INHERIT`/`ADMIN`, and reverse-membership paths) for application and retention roles.
- Enforced explicit table, column, sequence, schema, and function privilege matrices; revoked `PUBLIC` database `CREATE`, non-owner `GRANT OPTION`, and PostgreSQL 17+ `MAINTAIN`.
- Locked `utop14_app` `search_path` to `public, pg_catalog`.
- Verified via runtime `SET ROLE utop14_app` probes in `scripts/security_event_retention_verify.sql` that `utop14_app` cannot `UPDATE` or `DELETE` rows in `audit_logs` or `security_events` and cannot disable their append-only triggers.

### Retention Isolation and Catalog/GUC Hardening
- Restricted security-event pruning to a `SECURITY DEFINER` function owned by `utop14_retention_owner` and executable only by `utop14_retention_runner`.
- Enforced default-deny parameter ACLs (`SET` and `ALTER SYSTEM`) for `utop14_app`, retention roles, `utop14_schema_owner` (explicit grants), and `PUBLIC`.
- Enforced cross-database persistent GUC inspection (`pg_db_role_setting`) and fail-closed detection of sensitive cluster settings in `postgresql.auto.conf`.
- Closed the M14.3.19 temporary-catalog shadowing false PASS by qualifying all catalog relations, ACL helper functions, and `regclass` literals with `pg_catalog.`, pinning `SET search_path = pg_catalog, public` in provisioning/ownership scripts, and adding the live-catalog static guard (`tests/integration/test_security_catalog_qualification.py`).

## B-10 — DBA / Schema-Owner Trust Boundary (Project Owner Decision)

- **Formal Project Owner decision:**
  `ACCEPT — B-10 is accepted as an infrastructure trust boundary. The verifier's guarantees apply to application and retention roles. DBA/schema-owner authority remains outside that guarantee and must be governed through separate operational controls.`
- **Scope of guarantees:**
  - The technical guarantees of `scripts/security_event_retention_verify.sql` constrain `utop14_app`, `utop14_retention_owner`, and `utop14_retention_runner`.
  - Acceptance of B-10 does **not** eliminate DBA or `utop14_schema_owner` DDL/ownership authority and does **not** certify every future DBA control.
  - On `utop14_schema_owner`, PR #14 retains default-deny explicit parameter ACLs (implicit superuser privileges remain outside the ACL model) and restricts persistent GUCs to `search_path`, failing closed on unapproved role/database GUCs.

## Known Limitations at PR #14 (`d37648b61d0d5053cbd61c0ef4fc172f03d3d937`)

- **Schema owner login and superuser capability:** At PR #14, `utop14_schema_owner` was permitted to retain `LOGIN` and `SUPERUSER` attributes; neither `NOLOGIN` enforcement on `utop14_schema_owner` nor a separate `utop14_migrator` role was implemented in PR #14.
- **Terminology note (`OPS-01`) and follow-on migrator separation outside PR #14:** `README.md` uses the label `OPS-01` for the M14.3.3 four-role production ownership model (`utop14_schema_owner`, `utop14_app`, `utop14_retention_owner`, `utop14_retention_runner`) delivered with the ownership, provisioning, and verification scripts. By contrast, any separate follow-on migrator-separation workstream introducing a `NOLOGIN` `utop14_schema_owner`, a dedicated `utop14_migrator` login with `SET ROLE` enforcement in `migrations/env.py`, or base-role/prestep/rollback scripts is a separate workstream and is **not** part of PR #14 approval or M14.3 deliverables. Those migrator/`NOLOGIN` controls are not active as part of M14.3.
- **Point-in-time verification:** `scripts/security_event_retention_verify.sql` verifies catalog state at execution time; it does not prevent out-of-band drift between runs and cannot inspect non-catalog cluster configuration (`postgresql.conf`, CLI flags, environment — tracked as B-13).
